# ファイル操作と過去のタスクの復旧

サーバーモードはサーバー目録を直接利用し、ローカル初期化も整理案を準備しません。この記事は任意のローカル整理操作です。[サーバー原本と端末の目録](attachments.md)を参照してください。


サーバー移行は **設定 → 添付サーバー** でプレビューして実行します。アップロードと読み戻し検証後の原本はサーバー、移行済みのローカル原本は削除して軽量プレビューを保持し、永続的なローカル `originals/` アーカイブは追加しません。完全なローカル内容が必要な場合は **ローカルにキャッシュ** またはファイルを開く操作で取得してください。HTML プロジェクト資源はサーバー移行の対象外です。レガシー分は `scripts/localize_html_attachments.py` で `Web/` やプロジェクトの `assets/` へ移し、`_attachments` への整理は使わないでください。下記の `.vault-rag/attachment-migrations/` 復元ディレクトリはローカル整理用で、既存の履歴・回収記録は自動削除しません。旧リンクは LeafLoom 内で解決し、他のエディターとの互換性は保証しません。[サーバー添付とキャッシュ](attachments.md)を参照してください。


## できること

参照を確認して対応する添付の名前変更・移動・回収を行い、過去の復旧記録を保持します。

## 始める前に

構成変更前に保管庫をバックアップしてください。ローカル整理の入口は非表示のまま、サーバー移行は **設定 → 添付サーバー** にあります。新規保存先の変更で既存原本は移動しません。[添付の閲覧](attachments.md)も参照してください。

## 操作手順

1. 添付画面で対応ファイルを選び、名前変更・移動・回収を選びます。実行前に保存先、検出したノート参照、版と保護対象を確認します。
2. プロジェクト素材や未対応のサーバー操作は使用不可のままです。他の操作で迂回しないでください。参照が見つからないことは全参照の不存在を保証しません。
3. 復旧が必要な間は `.vault-rag/attachment-migrations/<job-id>/` の記録、原本、ノートの控えと `.vault-rag/trash/` を残します。入口を隠しても記録の削除や移行の自動再開は行いません。
4. アプリの端末専用領域にある送信待ち、サーバー参照と資料を保管します。使用中の SQLite を他の端末へコピーしたり、状態全体をキャッシュとして消したりしないでください。過去の作業を手動復旧する場合はタスク ID と機密情報を除いた診断をプロジェクトへ伝えてください。

## 完了後の状態

対応する操作を確認した場合にだけファイルを変更し、版とアクセス境界を再検証します。新規添付のサーバーを変えても既存原本や資料の紐付けは保持します。

## うまくいかないとき

版の変更、曖昧な参照、保護素材やサーバー能力の制限がある場合は停止し、復旧資料を保持して原因を解消してから再試行します。キャッシュはバックアップではなく、削除しても NAS 原本は消えません。
