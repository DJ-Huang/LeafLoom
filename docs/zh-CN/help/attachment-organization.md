# 文件操作与历史任务恢复

服务器模式直接使用服务器目录；本地初始化也不再准备整理方案。本文描述可选的本地文件整理操作，服务器用户参见[服务器原件与本机目录缓存](attachments.md)。


服务器迁移通过 **设置 → 文件与导入 → 附件存储** 单独预览和执行，上传、读回校验与旧路径映射完成后才释放本地原件，且不新增永久的本地 `originals/` 归档。下文的 `.vault-rag/attachment-migrations/` 恢复目录属于本地整理流程；已有历史与回收记录不会自动清除。旧链接在 LeafLoom 内继续解析，其他编辑器不保证兼容。详见[服务器附件与缓存](attachments.md)。


## 使用目标

带引用检查地重命名、移动或回收支持的附件，并保留旧版任务的恢复记录。

## 开始前

结构调整前先备份知识库。[0.1.5](../RELEASE_NOTES_0.1.5.md) 已隐藏迁移与整理入口，服务器设置只管理连接；切换新文件保存位置不自动迁移已有原件。详见[附件浏览](attachments.md)。

## 操作步骤

1. 在附件管理选择支持操作的文件，使用重命名、移动或回收。确认前核对目标位置、已发现笔记引用、文件版本和受保护资源。
2. 项目资源和服务器不支持的操作保持不可用，不要借其他附件操作绕过。“未发现引用”不表示已找全所有引用。
3. 仍需恢复时，保留 `.vault-rag/attachment-migrations/<job-id>/` 中的记录、原件和笔记备份，以及 `.vault-rag/trash/`。入口隐藏不会删除这些记录，也不会自动重新发起迁移。
4. 保留设备应用数据中的待上传文件、服务器引用映射和资料。不要跨设备复制使用中的 SQLite，也不要把整个状态目录当缓存清空。旧任务需要人工恢复时，向项目提供任务 ID 和去敏后的诊断信息。

## 完成后的表现

只有已确认、受支持的操作才会修改文件，并重新核对版本和边界。更改新附件默认服务器不会移动旧原件或改变资料库绑定。

## 没有成功时

遇到版本变化、引用不明确、资源保护或服务器能力限制时先停止，保留恢复材料并解决原因后再重试。下载缓存不是备份；清理它不会删除 NAS 原件。
