# 极空间官方附件桥接：恢复边界与调查记录

记录日期：2026-10-22。范围为本机 Mac 上的极空间官方客户端 `2.45.2026082601`。以下结论来自安装包程序和公开静态前端，不读取用户配置、密码、Cookie、Keychain、设备标识或私有会话存储。

**现有桥接可以被 LeafLoom 后台使用，但本轮没有确认可在附件窗口关闭或官方客户端重启后自动重建它的公开入口。** 客户端及附件窗口仍需保持开启，附件窗口可以最小化。自动检查健康、退避重试和提示恢复连接，不等于自动重建桥接。

## 程序证据

| 来源 | 观察 | 边界 |
| --- | --- | --- |
| 官方应用 `Contents/Info.plist` | 客户端版本为上述版本；未声明 `CFBundleURLTypes` | 当前安装包没有可据此调用的附件深链接协议 |
| `app.asar/background.js` 的 `MainThreadAction` → `remoteAccess` | `openlink` 进入原生 SDK，按登录中的官方客户端建立服务，再创建 `show:true` 的附件窗口 | 此 Electron IPC 是客户端内部调用，不是对外 HTTP API |
| 同一模块的 `Xc`、`Yc`、`Kc` | 启动时分别初始化服务映射、窗口数组及从10000开始的候选端口；关闭附件窗口时停止该服务并移除映射 | 全文件没有这些附件服务映射的持久化或启动重放逻辑；实际端口以 SDK 返回值为准 |
| 同一模块的启动和第二实例处理 | 启动恢复主管理通道；第二实例仅显示、聚焦主窗口；未找到 `open-url` 或 `setAsDefaultProtocolClient` 处理 | 未确认命令行或 URI 能打开指定附件服务 |
| `/home/static/js/index.1ba84a72.js` 的路由与分块定义 | 远程访问页面为 `/remoteAccess/nas`，使用 `async/85057.955f80b2.js` | 页面地址本身不是服务创建接口 |
| 上述远程访问组件 | `created` 只加载配置；`configRemoteUrl` 只打开编辑／新增框；`desktopVisible` 用于首页快捷方式 | 未发现“记住窗口”“启动恢复”“自动打开服务”或 keepalive 选项 |
| `background.js` 的 `powerMonitor.on('resume')` | 系统从睡眠恢复时调用 `Ne.refresh()`，进而调用 SDK 的 `libzrpc_refresh()` | 这属于存活客户端的刷新机制，不能作为窗口关闭或进程重启后服务自动重建的证据 |

原生创建链路使用下列内部调用；它不是可由 LeafLoom 直接调用的已公开协议：

```javascript
ipc.sendSync('MainThreadAction', 'remoteAccess', {
  act: 'openlink',
  item: {url: '127.0.0.1:8068/', https: 0, proxy: false}
});
```

服务创建后原生代码返回成功状态，不返回实际分配的本地端口；本地端口与 SDK 服务身份仅保存在客户端内存。附件窗口的 `closed` 处理会调用 `libzrpc_stop_service`。`checkRemoteAccessOpenApi` 只是原生能力探测，不能因名称中的 OpenApi 将其理解为后台开放接口。SDK 内嵌的 `/netinfo`、`/nasinfo`、`/debugui` 是传输诊断线索，本轮未找到可用于创建附件服务的公开 HTTP 路由。

## 本轮验证与未验证项

已有脱敏探测记录确认：当前建立的本地附件入口可接受独立后台请求；公开健康检查返回200，受保护资源要求附件服务自己的 Basic 认证。LeafLoom 不需要取得极空间登录凭据来使用这个已建立的数据通道。管理端口映射和附件映射是不同服务，不能通过替换管理 URL 的端口推导附件创建协议。

此次恢复调查只读取程序及公开静态资源，没有调用内部 IPC、SDK、登录或会话接口，没有读取上述诊断端点中的运行时信息，也没有关闭窗口、重启进程、调整网络或修改 NAS 配置。没有执行“关附件窗口后自动重建”“客户端退出后自动恢复”或睡眠／异地网络的端到端验收。

已有独立 HTTP 探测 helper 只验证已建立的附件数据通道，不负责官方客户端的登录与服务生命周期。它的成功记录不能作为自动重建能力的证据。

## 可交付的恢复行为

对已有桥接可以实现以下边界明确的诊断与恢复状态，具体是否已启用以当前版本实际实现和验收记录为准：

1. 只检查用户已确认、已配置的本地桥接地址。无凭据的公开 health 请求只能证明通道可达；后端 `poll_connections` 使用独立的附件 Basic 账号，对这个已配置 URL 发起认证 PROPFIND，确认 WebDAV 服务可用，不扫描其他端口，也不使用极空间登录凭据。不把登录页或重定向当作文件服务正常响应。这项认证探测已实现并通过模拟测试，最终安装环境验收尚未完成。
2. 短暂不可达时按有限退避重试，保留目录、缓存及待传任务；连接恢复后重新确认对象版本并继续允许的请求。
3. 地址持续不可达时说明需要检查官方客户端及附件窗口；窗口关闭或客户端重启后，要求重新打开既有附件入口，端口变化时更新配置。
4. 不扫描猜测端口并发送密码，不读取官方客户端会话，不加载其私有 SDK，不注入或改写客户端，也不把内部 IPC 包装成稳定公开接口。

本轮调查到此收敛。若未来官方提供可独立调用的服务创建与生命周期接口，应单独核验其认证、返回端口、重放和退出行为；当前不承诺这项能力。日常配置参见[附件存储架构](ARCHITECTURE.md#通用远程附件存储)与三语附件指南。
